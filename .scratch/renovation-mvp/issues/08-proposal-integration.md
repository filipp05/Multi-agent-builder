# 08: Полный путь с настоящей моделью и один пересмотр бюджета

**Что сделать:** Пользователь проходит весь путь от брифа до четырёх согласованных результатов и наблюдает один реальный пересмотр дорогого варианта через прораба.

**Зависит от задач:** 01: Живой бриф: пожелания → структурированные требования; 05: Технологические ограничения и совместимость материалов; 06: Точные упаковки, доставка и полный бюджет; 07: Независимый контроль и запрет ложного успеха.

**Статус:** черновик; после согласования — метка `ready-for-agent`.

**Ответственный:** A. **Сложность:** 5 баллов. **Этап:** MVP для предварительной защиты.

## Критерии приёмки

- [ ] Все семь ролей подключены через прораба. Специалисты не обходят проверки и не меняют общее состояние напрямую.
- [ ] Дизайн, технология, закупки, смета, график и аудит образуют согласованный комплект. Интерфейс показывает этапы и общую версию.
- [ ] Превышение бюджета или срока запускает не более одного цикла исправлений по разрешённой ветке. Нерешённый конфликт обозначается явно.
- [ ] Три прогона с настоящей моделью на обычном примере и примере превышения бюджета записаны с моделью, токенами и задержкой. Сохранённые ответы не выдаются за новые.
- [ ] Шесть основных сценариев предварительной защиты и чистый запуск Docker проверены вторым участником. README содержит фактическую модель, ограничения и сведения команды.
- [ ] Задача ограничена версией для предварительной защиты. Долговременное сохранение, расширение каталогов и улучшение оформления относятся к следующим задачам.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
