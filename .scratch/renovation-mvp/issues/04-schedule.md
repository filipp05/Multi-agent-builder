# 04: График ремонта по зависимостям

**Что сделать:** По примерному списку работ пользователь получает календарный график, видит технологическую паузу и объяснение задержки относительно желаемого срока.

**Зависит от задач:** Нет — можно начинать после согласования первой версии контрактов данных.

**Статус:** ready-for-agent. Общие контракты и критерии стыковки подготовлены в репозитории.

**Ответственный:** Карина (D). **Сложность:** 5 баллов. **Этап:** MVP для предварительной защиты.

## Критерии приёмки

- [ ] План работ принимается по первой версии контрактов. LLM-планировщик интерпретирует пожелания к календарю, а даты определяет алгоритм.
- [ ] Явно заданы одна бригада, рабочие часы, доступность поставок и технологические паузы. Интерфейс показывает зависимости и окончание ремонта.
- [ ] Публичный интерфейс проверки отклоняет цикл и неизвестную предшествующую работу. Работы не начинаются до поставки материалов.
- [ ] Есть пример с независимо рассчитанным расписанием и проверка объяснения конфликта сроков с настоящей моделью.
- [ ] D независимо от C составляет список обязательных статей для будущего аудита. Это эталон проверки, а не копия алгоритма сметы.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
