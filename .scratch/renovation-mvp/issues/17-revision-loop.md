# 17: Две ограниченные итерации и сравнение версий

**Что сделать:** Пользователь меняет бюджет или срок, видит предлагаемый компромисс и получает согласованный пересчёт с понятной разницей версий.

**Зависит от задач:** 08: Полный путь с настоящей моделью и один пересмотр бюджета; 09: Уточнение и подтверждение брифа; 11: Объяснимые совместимые аналоги.

**Статус:** черновик; после согласования — метка `ready-for-agent`.

**Ответственный:** A. **Сложность:** 5 баллов. **Этап:** полный учебный MVP.

## Критерии приёмки

- [ ] Разрешено не более двух циклов исправлений. Повтор решения и превышение лимитов приводят к явной остановке либо сообщению о нерешённых ограничениях.
- [ ] Изменение обязательного пожелания или состава работ требует решения пользователя. Отказ сохраняет прежнюю версию.
- [ ] Пометка зависимых результатов как устаревших предотвращает смешение старой сметы с новым товаром или графиком. Итог публикуется атомарно.
- [ ] Интерфейс сравнивает цену, срок и работы до и после. Приёмка проверяет изменение бюджета, срока и поступление устаревшего документа.
- [ ] Повторное использование результата разрешено только при совпадении отпечатка входных данных. Полный пересчёт остаётся безопасным запасным вариантом.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
