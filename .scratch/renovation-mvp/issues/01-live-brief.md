# 01: Живой бриф: пожелания → структурированные требования

**Что сделать:** Пользователь вводит описание и размеры в браузере и получает бриф от настоящей модели с явно указанными неизвестными. Это первый запускаемый в Docker сквозной пример и исходный вариант для сравнения качества извлечения требований.

**Зависит от задач:** Нет — можно начинать после согласования первой версии контрактов данных.

**Статус:** ready-for-agent. Общие контракты и критерии стыковки подготовлены в репозитории.

**Ответственный:** Филипп (A). **Сложность:** 5 баллов. **Этап:** MVP для предварительной защиты.

## Критерии приёмки

- [ ] Форма передаёт текст и размеры прикладному сервису. Ответ показывает размеры, обязательные и желательные требования, неизвестные данные.
- [ ] Настоящая модель возвращает бриф, проверенный по схеме. Некорректный JSON, пустой или обрезанный ответ не считаются успехом; проверяется поле `finish_reason`.
- [ ] После пробных вызовов выбран основной идентификатор модели. Фиксируются токены и задержка; ключ не попадает в HTML, журналы или образ Docker.
- [ ] Проверены сборка и запуск Docker, файл `.env.example` с примерами значений и инструкция. Приёмочный тест API выявляет отрицательные размеры и потерю указанного бюджета.
- [ ] Общий каркас приложения и первая версия контрактов данных готовы к подключению других частей. Для проверки этой задачи они ещё не требуются.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
