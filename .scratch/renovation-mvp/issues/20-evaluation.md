# 20: Сравнение одного агента и мультиагентной системы на отложенных сценариях

**Что сделать:** Команда получает воспроизводимый отчёт о корректности, полезности и стоимости разных способов организации агентов.

**Зависит от задач:** 12: Рабочий календарь и сроки закупок; 16: Доказательство, что контроль ловит ошибки; 17: Две ограниченные итерации и сравнение версий; 18: Осознанный выбор дизайна с техническими последствиями; 19: Сравнение корзин по полной стоимости.

**Статус:** черновик; после согласования — метка `ready-for-agent`.

**Ответственный:** D. **Сложность:** 5 баллов. **Этап:** полный учебный MVP.

## Критерии приёмки

- [ ] 24 сценария разделены до настройки: 12 для разработки и 12 для независимой оценки. У выполнимых случаев есть независимый допустимый эталон.
- [ ] Варианты B1/M1/M2 используют одинаковые данные, инструменты, модель и лимиты. Выполняются по три прогона на каждом из 12 отложенных сценариев либо явно описывается сокращение из-за квоты.
- [ ] Отчёт показывает число запусков и успехов по типам, устойчивость трёх повторов, стоимость успешного результата, задержки и ошибки. Улучшения не выдумываются.
- [ ] Результат можно воспроизвести через API и просмотр сохранённого плана. Проведены регрессионные проверки с настоящей моделью; версии инструкций, модели и данных сохранены.
- [ ] Вывод может быть в пользу одного агента. Принятое решение и ограничения выборки отражены в презентации.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
