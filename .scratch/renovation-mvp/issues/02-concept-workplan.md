# 02: Две концепции и состав работ для одной комнаты

**Что сделать:** По валидному примерному брифу пользователь видит две различные палитры/концепции, выбирает одну и получает список подготовительных и отделочных работ.

**Зависит от задач:** Нет — можно начинать после согласования первой версии контрактов данных.

**Статус:** черновик; после согласования — метка `ready-for-agent`.

**Ответственный:** B. **Сложность:** 5 баллов. **Этап:** MVP для предварительной защиты.

## Критерии приёмки

- [ ] У дизайнера и технолога отдельные инструкции и контексты; ответы проверяются по схемам `DesignConcept` и `WorkPlan`.
- [ ] Есть страница выбора концепции. Результат содержит устойчивые идентификаторы работ, категории материалов, пожелания и исключённые работы.
- [ ] Ограниченный словарь покрывает окраску стен и выбранный тип пола. Неизвестные категории не выдумываются.
- [ ] Тест на заданных данных проверяет сохранение обязательных пожеланий и подготовительные работы. Настоящий вызов модели проверяет смысловую часть.
- [ ] Страница работает отдельно на примере по первой версии контрактов; после задачи 01 подключается адаптером без переписывания предметной логики.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
