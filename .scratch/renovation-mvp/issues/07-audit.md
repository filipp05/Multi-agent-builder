# 07: Независимый контроль и запрет ложного успеха

**Что сделать:** Пользователь видит отчёт контролёра с конкретными пропусками и дублями. Статус «проверено» недоступен, пока существенные замечания не устранены.

**Зависит от задач:** 04: График ремонта по зависимостям.

**Статус:** ready-for-agent. Общие контракты и критерии стыковки подготовлены в репозитории.

**Ответственный:** Карина (D). **Сложность:** 5 баллов. **Этап:** MVP для предварительной защиты.

## Критерии приёмки

- [ ] Контролёр восстанавливает ожидаемый состав расходов по первичным данным в отдельном контексте. Самооценка сметчика не доказывает правильность.
- [ ] Код проверяет суммы, ссылки, единицы, полноту, даты и версии. LLM проверяет смысл и подкрепляет замечания данными.
- [ ] Интерфейс показывает важность замечания, затронутую строку, причину и требуемое исправление. Неполная проверка отличается от найденной ошибки.
- [ ] Намеренно внесённые пропуск и дубль обнаруживаются. Неизвестная доставка и нарушенный срок исключают ложный статус «проверено».
- [ ] Проверка работает на независимом примере `PlanBundle`, не ожидая интеграции 08. Формат позволяет затем принять настоящие результаты агентов.

## Граница задачи

Реализовать один описанный пользовательский путь: контракт данных → прикладной сервис и API → минимальный интерфейс → проверка результата. Не добавлять функции соседних задач. В задачах 01–07 допустимы отдельные тестовые примеры; в задаче 08 те же контракты должны работать в общем потоке через прораба.

## Передача и проверка

Приложить пример входа и выхода, результаты приёмочных проверок, ограничения и журнал настоящего вызова модели, если он предусмотрен задачей. Проверка по кольцу: A → B → C → D → A; стрелка означает «проверяет работу». C и D дополнительно независимо сверяют численные эталоны. Если задача не помещается в одну рабочую сессию, до реализации разделить её по пользовательскому поведению, сохранив зависимости.
