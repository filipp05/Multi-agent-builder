# Контракты команды: как состыковать четыре части

**Версия 0.1.0 — предложение для согласования.** Контракт — договор о том, какие данные каждая часть принимает и возвращает. Схемы, примеры и проверки уже работают; само приложение ещё предстоит собрать.

Сначала прочитайте эту страницу, затем [правила полей и расчётов](RULES.md). Точные имена и типы полей заданы в [схеме комплекта](schemas/plan.schema.json), исход этапа — в [схеме ответа](schemas/stage-result.schema.json). При расхождении текста и схемы исправляем оба документа до объединения изменений.

## Кто что передаёт

Все результаты получает и сохраняет прораб. Участники не вызывают чужих агентов напрямую. Одна программа на Python, а не четыре сервиса.

| Этап | Кто отвечает | Что получает | Что возвращает |
|---|---|---|---|
| `brief` | Филипп | Пожелания пользователя | Размеры, бюджет, сроки, ограничения, рабочий календарь |
| `design_options` | Миша | `brief` | Две дизайн-концепции |
| `design_selection` | Филипп | `design_options` и выбор пользователя | Идентификатор выбранной концепции |
| `work_plan` | Миша | `brief`, `design_selection` | Работы, зависимости, трудозатраты, потребности в материалах |
| `procurement` | Олег | `work_plan`, снимок каталога | Конкретные упаковки, предложения и доставка |
| `estimate` | Олег | `work_plan`, `procurement`, источники тарифов | Материалы + работа + доставка + резерв |
| `schedule` | Карина | `brief`, `work_plan`, `procurement` | Даты работ с учётом поставок и пауз |
| `audit` | Карина | Все семь предыдущих документов | Замечания и результат независимой проверки |

Восемь документов — это восемь результатов, а не восемь агентов: выбор делает пользователь через прораба. Общий реестр источников и каталог доступны этапам только для чтения. Требования и выбранную концепцию прораб разрешает по ссылкам на документы, а не пересказывает текстом.

## Как начать независимо от остальных

1. Установить Python 3.12 и зависимости: `python -m pip install -r requirements-contracts.txt`.
2. Запустить `python -m pytest -q` из корня репозитория.
3. Открыть [успешный пример](examples/completed.json), взять входные документы своего этапа и заменить его результат своим.
4. Проверить собранный комплект: `python -m contracts.validate contracts/examples/completed.json`.
5. Добавить свой пример и проверку отказа на неправильных данных. Отдать изменение вместе с проходящими проверками.

[Пример превышения бюджета](examples/over-budget.json) тоже корректен: контракт допускает честный ответ «ограничения не выполнены». Он не должен превращаться в успешный результат.

## Как вызывается этап

Общий интерфейс уже задан в `contracts/handoff.py`: `handler(context) → (result, artifact_or_none)`. Прораб выбирает обработчик по `context.stage` и вызывает через `call_stage`. `context` содержит `schema_version`, `project_id`, `run_id`, `revision`, `stage`, `input_artifact_ids`, прямые входы `input_artifacts`, связанные документы `referenced_artifacts`, снимок `sources` и `offers`. Для первого этапа дополнительно передаётся `user_request`, для выбора — `selected_concept_id`. Это интерфейс внутри приложения; HTTP API сейчас не зафиксирован и не реализован.

`result` соответствует схеме ответа этапа. При `ok` рядом возвращается один документ, а `artifact_id` ссылается на него. При `needs_input` возвращаются вопросы и нет документа. При `failed` возвращается ошибка и нет документа. Прораб проверяет совпадение проекта, запуска, версии, вида и идентификатора, прежде чем принять документ. Незнакомый этап или лишнее поле — ошибка, а не попытка угадать смысл.

Примеры: [успех](examples/stage-ok.json), [нужен ответ пользователя](examples/stage-needs-input.json), [ошибка](examples/stage-failed.json). Проверка ответа: `python -m contracts.validate contracts/examples/stage-ok.json --stage`.

Схема комплекта описывает **завершённый проход**, а не промежуточное состояние графа. До сбора восьми документов Филипп хранит частичные результаты отдельно. Функция `validate_stage_output(result, artifact, context)` проверяет пару «ответ + документ», принадлежность текущему запуску и ожидаемые входы. В проверочный `context` координатор передаёт общие идентификаторы, `stage` и `input_artifact_ids`. Подключение этой проверки к движку остаётся задачей интеграции.

## Что считается готовым

`completed` разрешён только при полном комплекте, пройденной проверке, известной стоимости и сроках, соблюдении бюджета и срока, отсутствии неподдерживаемых работ и неизвестного основания. В остальных случаях итог — `constraints_unresolved` с понятной причиной пользователю.

Проверки контракта защищают форму, ссылки и арифметику. Они **не доказывают** достоверность цен, строительную безопасность или качество дизайна. Контролёр Карины должен независимо пересчитать контрольные примеры, а не просто вызвать этот же проверяющий код.

## Как менять договор

Не переименовываем поле в одиночку. Предлагаем изменение схемы, обновляем примеры и проверки, согласуем с владельцами затронутых этапов. До сборки версии 0.1.0 изменения обсуждаем вместе. После фиксации несовместимое изменение получает новую версию; смешивать версии в одном комплекте запрещено.

## Проверка передачи между участниками

`python -m contracts.handoff contracts/examples/completed.json`

Команда проверяет восемь последовательных передач на готовом примере и повторно проверяет собранный комплект. Это проверка договора без LLM, не демонстрация работающих агентов.

`make_context` формирует входы из уже принятых документов. В `input_artifacts` лежат прямые входы этапа; в `referenced_artifacts` — их предшественники для разрешения ссылок. Например, план работ получает выбор напрямую и выбранную концепцию через связанный документ. Будущие результаты туда не попадают. Оба пользовательских поля присутствуют всегда; вне соответствующего этапа равны `null`.

`call_stage` передаёт обработчику копию контекста и проверяет ответ по исходному контексту. Обработчик не может поменять ревизию входа, чтобы принять свой устаревший результат. Сохранение, повторные вызовы, запросы уточнений и реальный выбор обработчиков реализуются в приложении Филиппа.
