# Архитектура текущего MVP

Один FastAPI-процесс, SQLite и фиксированный последовательный workflow. Вход пользователя подтверждается до расчёта; концепцию выбирает пользователь. Семь функциональных ролей не означают семь моделей или свободно договаривающихся агентов.

```text
Пользователь → brief → подтверждение
                    → design → две концепции → выбор пользователя
                             → план работ (Python)
                             → procurement → закупки и смета
                             → planning → календарь и аудит
                             → результат с явным статусом
```

## Модули и интерфейсы

| Модуль | Вход → выход | Что важно вызывающему коду |
|---|---|---|
| `brief` | пожелания/ответы → подтверждённый `brief` | версия состояния, идемпотентные действия, пользовательское подтверждение |
| `design` | `brief` → `design_options`; выбор → `work_plan` | только поддерживаемая геометрия/работы; два технологических профиля; неподтверждённые исключения отклоняются |
| `procurement` | потребности + снимок каталога → `procurement`, `estimate` | LLM выбирает только допустимые товары; количество упаковок и деньги считает код |
| `planning` | первичные документы → `schedule`, `audit` | независимые расчётные проверки и отдельный смысловой вызов; замечания не скрываются |
| `pipeline` | подтверждённый проект + действие → сохранённый запуск | один расчёт одновременно; устаревшая версия отвергается; явная остановка/повтор |
| адаптер модели | `ModelRequest` → `ModelReply` | JSON-схема, timeout, нормализованные ошибки, метаданные |

`contracts/` задаёт интерфейсы между этапами. Общая точка запуска — `app.main:app`. Специализированные веб-страницы модулей остаются вспомогательными.

Codex и Bedrock удовлетворяют общему интерфейсу модели. Исторически типы и реализация Codex находятся в `app/brief/model.py`; Bedrock — в `app/providers/bedrock.py`. Вынос общего интерфейса в отдельный пакет возможен позже, но не нужен для этого переезда.

## Состояние и воспроизводимость

Бриф и полные планы хранятся в SQLite в `RENOVATION_DATA_DIR`; идентификаторы проекта, запуска и ревизии связывают документы. Редактирование брифа делает прошлый результат устаревшим. После перезапуска незаконченный план становится `interrupted`; автоматического платного продолжения нет. Docker требует один worker и постоянный volume.

Цены, правила совместимости и нормы — версионированные учебные данные. В документах сохраняются ссылки на источники; это не актуальные магазинные предложения. Арифметику и календарь модель не заменяет.

## Ограничения и следующие решения

- Автоматического цикла «аудитор → адресное исправление → повторный аудит» пока нет.
- Включены покраска и ламинат вместе. Произвольные исключения нельзя надёжно классифицировать строковыми эвристиками: допускаются только точные известные исключения из вне-MVP списка (`потолок`, `мебель`, `электрика`, `сантехника`, `перепланировка`; регистр и крайние пробелы несущественны). Остальное требует уточнения; пользовательское ограничение не удаляется автоматически.
- Аудит старого/импортированного плана с непроверенными исключениями не возвращает `passed`.
- Целевые изображения/3D и визуализация исполнения агентов требуют отдельного согласования объёма. Их нет в текущем MVP.
- Сравнение с одним большим prompt и массовая сквозная оценка нужны для утверждений о превосходстве архитектуры.
