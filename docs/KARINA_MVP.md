# График и контроль: этап D (Карина)

Требования, план работ и закупки → график ремонта → независимая проверка всего комплекта. Задачи [04 — график](../.scratch/renovation-mvp/issues/04-schedule.md) и [07 — аудит](../.scratch/renovation-mvp/issues/07-audit.md).

Код рассчитывает даты и проверяет числа. Модель объясняет график и ищет смысловые пропуски в отдельном контексте. Входные документы для самостоятельного запуска берутся из [общего учебного примера](../contracts/examples/completed.json); на странице они обозначены как готовые данные.

## Запуск

Из корня репозитория, в активированном виртуальном окружении после установки `requirements-dev.txt` (см. [FILIPP_MVP.md](FILIPP_MVP.md)):

```sh
python -m app.karina.cli
python -m app.karina.cli --model
python -m uvicorn app.karina.api:app --host 127.0.0.1 --port 8002
```

Страница: http://127.0.0.1:8002/karina/. Можно изменить календарь, построить график и проверить комплект. Отдельный режим проверяет присланный график, сохраняя его даты, — это удобно для проверки ошибок.

Для режима с моделью нужны Codex CLI и вход через ChatGPT. Используется общий `CodexModel` Филиппа, по умолчанию `gpt-6-astra` с reasoning `low`; модель задаётся через `KARINA_MODEL`. Без модели выполняются программные проверки, а аудит получает статус `incomplete`.

## Устройство

- `app/karina/schedule.py` — график одной бригады: зависимости, рабочие дни и часы, доступность материалов. Работы не пересекаются; сушка продолжается ночью и в выходные, последняя пауза входит в дату окончания. Циклы и ссылки на неизвестные работы дают понятный отказ.
- `audit.py` — независимый пересчёт упаковок, сумм, доставки и резерва; поиск пропусков и дублей; проверка ссылок, версий и ограничений графика. Расчётные функции Олега и построитель графика для сверки не вызываются.
- `data/control-rules.json` — контрольные нормы и тарифы учебного примера.
- `agents.py`, `prompts/` — объяснение рассчитанного графика и отдельный смысловой контролёр. Модель добавляет замечания, каждое со ссылкой на документ или строку; программные ошибки она удалить не может.
- `stages.py` — обработчики `schedule_handler()` и `audit_handler()` по общему интерфейсу `handler(context) → (result, artifact_or_none)`.
- `service.py`, `api.py`, `static/` — сборка результата, API и страница.

## Пример

Рабочая неделя — понедельник–пятница, смена 09:00–17:00. Материалы доступны к началу ремонта, каждая работа занимает восемь рабочих часов.

| Работа | Дата и время | Пауза после работы |
|---|---|---|
| Подготовка | 26.10.2026, 09:00–17:00 | — |
| Окраска | 27.10.2026, 09:00–17:00 | 16 часов сушки |
| Укладка пола | 28.10.2026, 09:00–17:00 | — |

Окончание ремонта — **28.10.2026 в 17:00 МСК**. Поздняя поставка сдвинет соответствующую работу и зависящие от неё этапы. Если желаемый срок раньше рассчитанного, результат покажет нарушение срока и его причину.

Аудит возвращает один из трёх статусов:

| Статус | Значение |
|---|---|
| `passed` | Программная и смысловая проверки завершены без блокирующих замечаний и неизвестных данных. |
| `failed` | Найдена блокирующая ошибка, например пропущенная статья или нарушенная пауза. |
| `incomplete` | Для проверки недостаточно данных либо смысловой контролёр не запускался. |

Правильно рассчитанный план может превышать бюджет или срок. В этом случае общий результат — `constraints_unresolved`; для `completed` нужны успешный аудит и выполнение обоих ограничений.

Примеры выходов: [график](../app/karina/examples/schedule.json), [аудит без модели](../app/karina/examples/audit-program-only.json).

## Подключение к общему сценарию

Подключение обработчиков к сценарию Филиппа относится к задаче 08. Для передачи документов используются общие `make_context` и `call_stage` из `contracts.handoff`:

- График принимает `brief`, `work_plan`, `procurement` и возвращает `schedule`.
- Аудит принимает все семь предыдущих документов текущего запуска и возвращает `audit`.
- Для полного аудита сначала вызывается `agents.review_bundle(model, audit_context, rules)`, затем проверенные `reply['findings']` передаются в `audit_handler(semantic_findings=...)`. Без этого проверка остаётся `incomplete`.

Координатор назначает идентификаторы и версии документов, хранит результаты и включает источник контрольных правил `load_rules()['source']` в снимок источников запуска.

Страница и API подключаются к общему FastAPI-приложению через `app.karina.api.configure(app, model=shared_model)`. Маршруты: `GET /karina/api/example`, `POST /karina/api/run`, `POST /karina/api/audit`.

## Проверки

```sh
python -m pytest -q tests/karina
```

Проверяются календарный эталон, выходные и паузы, поставки, пропуски и дубли, суммы, версии, ошибки модели, API и страница. 

## Ограничения

- MVP рассчитан на одну комнату и одну бригаду; часовой пояс — Москва.
- Цены, нормы и тарифы учебные. Для другой технологии или источника ставок нужны соответствующие контрольные правила.
- Неизвестные даты поставки, суммы или нормы приводят к неполному результату проверки.
- Самостоятельный сервис не хранит историю проектов; хранение относится к общему координатору.
