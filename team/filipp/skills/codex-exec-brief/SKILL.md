# Codex exec для прораба

## Зачем

`codex exec` — неинтерактивный запуск Codex: приложение передаёт пожелания и получает структурированный ответ без ручного копирования из чата. В нашем MVP модель извлекает факты и неоднозначности; Python проверяет данные, хранит диалог и разрешает подтверждение только пользователю. Это модель первого этапа, не замена остальных агентов ремонта.

Процесс CLI локальный, **инференс удалённый**: переданные пожелания отправляются в сервис Codex. Используем вход ChatGPT по подписке; ограничения подписки сохраняются. Отдельный API-ключ и автоматическое платное переключение в этом проекте не используются. Opus-оценщик — отдельный, явно оплачиваемый контур, не fallback.

## Перед запуском

Работай из корня репозитория. Прочитай `app/filipp/model.py` (актуальные аргументы и изоляция) и `app/filipp/service.py` (схема источников). Для изменения извлечения дополнительно прочитай `app/filipp/prompts/brief.txt`, `app/filipp/schemas/extraction.schema.json` и `contracts/RULES.md`.

```sh
codex --version
codex login status
```

Продолжай модельный вызов только при входе через ChatGPT. Если входа нет, предложи пользователю `codex login`; логин и лимиты не обходить другим провайдером. Проверенная версия в исходном измерении —0.155.1; после обновления перепроверь `codex exec --help`, smoke и изоляцию. Само наличие CLI не доказывает доступ к выбранной модели.

Окружение приложения: Python3.12; зависимости `requirements-app.txt`. Для тестов — `requirements-dev.txt`. Если окружения нет:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

## Как вызвать

Используй существующий `CodexModel.generate(ModelRequest(...))`, а не копию subprocess-кода. `ModelRequest` принимает instruction, data, schema и timeout_s; результат — `ModelReply.data` и metadata либо `ModelError`.

Адаптер собирает `codex exec --json --output-schema … -`, передаёт данные через stdin и запускает процесс во временной папке. Полный список флагов — в `isolated_args()`, единственном источнике конфигурации. `--json` даёт поток событий NDJSON; `--output-schema` задаёт структуру ответа. Это разные уровни формата.

Минимальная проверка с настоящей моделью:

```sh
.venv/bin/python scripts/filipp_codex_smoke.py
```

Ожидается exit0 и `status=ok`; результат сохраняется локально в `.scratch/filipp-mvp/results/smoke.json` (следующий запуск перезапишет его). `--extraction` добавляет пробу извлечения; для полной пользовательской цепочки запускай приложение:

```sh
.venv/bin/python -m uvicorn app.filipp.api:app --host 127.0.0.1 --port 8000
```

Открой `http://127.0.0.1:8000`: пожелания → уточнения → сводка → явное подтверждение. Продовый путь через Service дополняет JSON Schema точным enum доступных input_id; smoke с общей схемой не заменяет эту проверку.

## Инварианты интеграции

- Сохраняй `safe_environment()` и конфигурацию изоляции: вход ChatGPT, без API credentials/fallback, без инструментов модели, пользовательских навыков и чтения проекта. Не ослабляй ограничения ради успешного smoke. Ошибка внешнего sandbox означает необходимость разрешённого запуска, а не изменения защиты адаптера.
- Exit0 недостаточно: разбери NDJSON, выбери ответ агента, проверь JSON Schema. Известное `Reconnecting...` допустимо только при новом сообщении после него и последующем `turn.completed`; `turn.failed`, неизвестные error и незавершённое восстановление остаются отказами.
- Сохраняй точные input_id и цитаты. Service проверяет происхождение факта; UUID и цитаты не исправляются догадкой. Затем проверяются размеры, деньги, даты, конфликты и границы работ. Валидный JSON сам по себе не означает достоверных требований.
- Не добавляй повторы invalid_response «до успеха». Адаптер ограниченно повторяет только распознанные временные ошибки; auth/quota требуют остановки и понятного сообщения. При сбое используй metadata.diagnostic: этап, хеш/размер, тип исключения, путь схемы. Сырые ответы в рабочий журнал не добавляй; отдельный локальный захват допустим для заранее синтетических диагностических данных.
- Независимые сценарии запускай постоянным ограниченным пулом; внутри одного диалога шаги последовательны. Пример проверенной нагрузки — два независимых прогона по3 workers. При лимите прекращай новые старты; параллелизм не отменяет лимитов подписки.

## Как проверить результат

Быстрые тесты без модели:

```sh
.venv/bin/python -m pytest -q tests/filipp/test_model.py tests/filipp/test_reliability.py
```

Полный pytest включает Chromium; установи браузер в используемый тестами локальный каталог:

```sh
PLAYWRIGHT_BROWSERS_PATH="$PWD/.scratch/filipp-mvp/runtime/browsers" .venv/bin/python -m playwright install chromium
.venv/bin/python -m pytest -q
```

Настоящее измерение запускай отдельно и только в объёме задачи. Пример одного диагностического dev-сценария (имя каталога выбери новое):

```sh
.venv/bin/python -m evals.filipp.run --split dev --limit 1 --repeats 1 --concurrency 1 --name codex-smoke-dev-001
```

Проверь `summary.json`, ошибки и gate: exit0 означает завершённый прогон, а не прохождение приёмки. Полная регрессия —20dev+10известных holdout, по3повтора, пороги в `evals/filipp/manifest.json`. Исходники и параметры замораживаются; после изменений используй новое имя запуска, сохраняй прежние неудачи.

В результате работы укажи версию CLI/модель, что реально запустила, ошибки и ограничения, пути локальных результатов. Разделяй тесты без модели, настоящий Codex и платную разметку. Секреты, SQLite, логи, ответы и личные настройки остаются локально.
